# Report
### Report author: rmackay9
### Report Time: May 12, 2020
### Report Content:
EKF2 and EKF3's beacon support is broken in SITL and perhaps on real vehicles.  I suspect the changes to how the AHRS origin is being set are partially to blame (beacon's are the one sensor that can provide an origin).  
In SITL (at least) there are two problems:  
- the user must set the EKF origin by right-mouse-clicking on the map (this was not necessary previously)  
- the vehicle moves wildly around on the map  
To reproduce the problem in SITL:  
- Enable EKF3 (EKF3 is the better choice for Beacons)    
- param set EK3_ENABLE 1    
- param set EK2_ENABLE 0    
- AHRS_EKF_TYPE 3    
- param set EK3_GPS_TYPE 3  
- param set GPS_TYPE 0  
- param set BCN_TYPE 10  
- param set BCN_LATITUDE -35.363261  
- param set BCN_LONGITUDE 149.165230  
- param set BCN_ALT 584  
- param set BCN_ORIENT_YAW 45 (really?)  
The vehicle should automatically appear on the map (but it doesn't) so if using MAVProxy, right-mouse-button-click and "Set Origin (with Altitude)" and the vehicle will appear but then begin moving wildly.  
To resolve the issue we should probably confirm that the AP_Beacon_SITL class is calculating reasonable distances.  This could be done without enabling the EKF to use the Beacons so we can maintain control of the vehicle (i.e. leave GPS_TYPE = 1, EK3_GPS_TYPE = 0).  
The next step would be to confirm these values are making it into EKF3.  Finally we should investigate what's wrong with setting the origin, it's reasonable to remove the BCN_LATITUDE, LONGITUDE and ALT parameters though because this method of setting home is inconsistent with other sensors.  
PR \\\#14345 partially addresses an issue with the Beacon autotest but does not fix the issues mentioned above.
